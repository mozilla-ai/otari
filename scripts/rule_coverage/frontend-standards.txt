# Rule-coverage manifest: the frontend-standards skill against the instructions
# CodeRabbit reads.
#
# Pair:
#   skill        .github/skills/frontend-standards/*.md
#   instructions .github/instructions/frontend-standards.instructions.md
#
# tests/unit/test_frontend_rule_coverage.py checks this file against both from
# the same commit: every `##`/`###` heading in the skill must appear here under
# [covered] or [excluded], every entry here must still name a heading that
# exists, every rung named here must still be numbered in the instructions, and
# every rung the instructions state must be named by at least one heading. So
# adding a section to a topic guide fails the repository's own tests until
# somebody decides whether a reviewer needs it. That is the point: the decision
# is a sentence of work at the moment it is cheap, rather than a discovery
# months later that nothing was ever compared.
#
#   [covered]   a numbered rung in the instructions carries this heading's rule
#   [excluded]  a reviewer needs nothing from it; give a reason
#
# The instructions are a deliberate compression rather than a mirror, so one
# rung carries several headings and [excluded] is the common answer. Much of the
# skill is how to write code rather than what to flag in a diff. Three reasons
# recur, and they are the ones to reach for: the section is an index or a digest
# of sections classified elsewhere; a test or a lint already fails on it, so
# review adds nothing; or the finding is not visible in a diff at all.
#
# Entries are `<file> :: <heading>` with an optional `# reason` trailer, which
# [excluded] requires. Under [covered] a `rung <n>` line opens the run of
# headings that rung carries. Blank lines and `#` lines are ignored.
#
# Renaming a heading reads here as a delete plus an add. That is the same trade
# scripts/sdk_codegen/sdk-endpoints.txt makes with a route path, and the fix is
# the same: edit one line.
