# Web Dashboard (`web/`)

`web/CLAUDE.md` is a one-line `@AGENTS.md` import of this file. Always edit `AGENTS.md` directly; never modify `CLAUDE.md`, and do not delete it: Claude Code discovers `CLAUDE.md`, not `AGENTS.md`, so the import is what loads this file.

Loaded when working under `web/`. For house style (HeroUI v3, `--otari-*` design
tokens, TanStack Query, Vitest), read
[../.github/skills/frontend-standards/SKILL.md](../.github/skills/frontend-standards/SKILL.md).

- The standalone admin dashboard is a React + HeroUI v3 SPA in `web/` (Vite, Tailwind v4, TanStack Query). It browses the model catalogue, sets model pricing, manages routing policies (which absorbed the old Aliases page), adds/edits provider API keys, and toggles runtime settings; it calls the management API (`/v1/models`, `/v1/pricing`, `/v1/routing/policies`, `/v1/aliases`, `/v1/provider-credentials`, `/v1/settings`) as the master key: entered once on a sign-in screen, the key is exchanged (`POST /v1/auth/session`) for an HttpOnly session cookie with a TTL (`dashboard_session_ttl_hours`, table `dashboard_sessions`), so the raw key is never persisted in the browser and a sign-in survives tab closes and restarts. The auth dependencies in `api/deps.py` accept the cookie only when a request carries no header credentials; master-key rotation revokes every session and re-mints the caller's.
- Runtime search tools: the Tools & Guardrails page (`web/src/pages/ToolsGuardrailsPage.tsx`) renders `web/src/components/SearchToolsCard.tsx`, which manages the `search_tool_credentials` table via `/v1/search-tools` (CRUD + `GET /providers` for the picker). Backend: `services/search_tool_store_service.py` overlays stored tools onto `config.search_tools` exactly as the provider store overlays `config.providers` (per-config baseline on `config._search_tool_baseline`, TTL refresher wired in the lifespan, standalone-only), so `POST /v1/search` no longer needs a config file. Config-file tools are listed read-only.
- Runtime provider management: the Providers page (`web/src/pages/ProvidersPage.tsx`) manages the `provider_credentials` table via `/v1/provider-credentials` (CRUD + `POST /{instance}/test`). Backend: `services/provider_store_service.py` overlays stored providers onto `config.providers` (per-config baseline on `config._provider_baseline`, refreshed by a TTL refresher wired in the lifespan like the alias refresher, standalone-only); `services/secret_box.py` encrypts keys with `OTARI_SECRET_KEY` (Fernet); `services/master_key_service.py` generates + prints a master key on first run when none is set (hash in `runtime_settings`). Keys are write-only over the API (responses expose only `last4`).
- Build: `make dashboard` from the repo root (`npm --prefix web ci && npm --prefix web run build`). Output goes to `src/gateway/static/dashboard/` (set in `web/vite.config.ts`), which is gitignored, not committed: Vite content-hashes every asset filename, so a committed bundle turned any two branches touching `web/src` into a merge conflict. Consequences: the Docker image builds the bundle in a `node:22-slim` stage (`Dockerfile`), a source checkout without a build degrades to the tutorial page (`gateway/dashboard.py` returns `None`), and a wheel ships the dashboard only if `make dashboard` ran first. There is nothing to commit after a `web/src` change.
- Bundled user guide: the dashboard renders `docs/dashboard.md` at `/#/docs` (linked from the sidebar footer) by importing it with Vite's `?raw` (`web/src/pages/DocsPage.tsx`), so the running dashboard ships the guide it matches. The guide lives outside `web/`, so `web/vite.config.ts` grants `server.fs` access to it. Because it is a build input from outside `web/`, it is also a Docker image input: `.dockerignore` excludes `docs/` but re-includes this one file, and `otari-docker.yml` triggers on it.
- Home-screen install (PWA): `web/public/pwa/` holds the web app manifest and the PNG app icons (`icon-192`, `icon-512`, a `maskable` 512, and an `apple-touch-icon` for iOS), all generated from the Otari mark in `web/public/favicon.svg` (white mark on `--otari-brand`). Vite copies the directory into the bundle and `src/gateway/main.py` mounts it at `/pwa` alongside the dashboard, so it is standalone-only; `web/index.html` links the manifest plus the `apple-*`/`theme-color` meta tags. There is deliberately no service worker: Chrome dropped the fetch-handler requirement for menu installs, and the dashboard is live API data with nothing worth caching offline.
- Checks: `npm --prefix web run typecheck`, `npm --prefix web test`. CI runs these plus a build, to prove the bundle the Docker image produces still compiles (`.github/workflows/otari-dashboard.yml`).
- End-to-end (`web/e2e`, `npm --prefix web run e2e`, also a CI job): Playwright against a real gateway serving the freshly built bundle (`e2e/serve.sh` wipes a SQLite DB and boots standalone; `e2e/otari.yml` fixes the master key). Three ordered projects share that one database, so the order is declared in `playwright.config.ts` rather than left to filename sort: `onboarding` (`dashboard.spec.ts`) needs the empty DB and asserts the first-run screens; `seed` (`parity.setup.ts`) imports the usage fixture in `e2e/parity-data.ts` through `POST /v1/usage/external-events`, which writes real priced usage rows with no upstream to reach; `parity` (everything else) then asserts Overview, Activity, Usage and the management pages behave. These pages are gateway-wide, so each spec scopes itself to what it owns rather than to a global count: Activity filters on the fixture's `source`, Usage names its models, sessions and users, the management specs create and remove their own objects, and Overview asserts a floor because its tiles cannot be filtered at all. Shared locators live in `e2e/helpers.ts`; note that an open react-aria combobox popover `aria-hidden`s the rest of the page, so `dismissComboBox` has to run before asserting anything outside it.
- Serving: standalone mode serves `index.html` at `/` and hashed assets under `/assets` (`src/gateway/main.py`, `src/gateway/dashboard.py`); the get-started tutorial moved to `/welcome`. Hybrid mode has no local management API, so `/` keeps serving the tutorial. Client-side routing uses react-router's `HashRouter` (routes live under `/#/providers`, `/#/models`, `/#/routing`, `/#/settings`; `/#/aliases` redirects to `/#/routing`, which absorbed it), so hash routes need no server catch-all and the API/asset paths are never shadowed.
