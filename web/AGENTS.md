# Web Dashboard (`web/`)

`web/CLAUDE.md` is a one-line `@AGENTS.md` import of this file. Always edit `AGENTS.md` directly; never modify `CLAUDE.md`, and do not delete it: Claude Code discovers `CLAUDE.md`, not `AGENTS.md`, so the import is what loads this file.

Loaded when working under `web/`. For house style (HeroUI v3, the semantic design
tokens, TanStack Query, Vitest), read
[../.github/skills/frontend-standards/SKILL.md](../.github/skills/frontend-standards/SKILL.md).

- The standalone admin dashboard is a React + HeroUI v3 SPA in `web/` (Vite, Tailwind v4, TanStack Query): model catalog, pricing, routing policies, provider keys, users, budgets, usage, runtime settings. It calls the management API as the master key, entered once on a sign-in screen and exchanged (`POST /v1/auth/session`) for an HttpOnly session cookie with a TTL (`dashboard_session_ttl_hours`, table `dashboard_sessions`), so the raw key is never persisted in the browser and a sign-in survives tab closes and restarts. The auth dependencies in `api/deps.py` accept the cookie only when a request carries no header credentials; master-key rotation revokes every session and re-mints the caller's.
- Deployment bootstrap: `src/main.tsx` fetches `GET /v1/bootstrap` (`src/gateway/api/routes/bootstrap.py`, mounted in both modes, unauthenticated) *before* it mounts React and hands the answer to `App`, which picks one of three roots from it: the hybrid landing page, the sign-in screen, or the router. A bootstrap that did not answer is an error state, never a guessed deployment. Below that, `src/shared/hooks/useDeployment.tsx` provides it, so a feature reads `useDeployment()` / `useSurfaces()` and no page component branches on the gateway's mode. The OSS half of the contract in mozilla-ai/otari-ai#1591, which is why the enum carries values (`hosted`, `hosted_user`) this gateway never produces.
  - A *surface* is the deployment axis: the management API groups a standalone gateway serves (`STANDALONE_SURFACES`), which is why a nav item gates on `usage` rather than "Activity", both being views over `/v1/usage`. A hybrid gateway hosts none. Deliberately **not** called capabilities, which otari.ai spends on the entitlement axis; the two vocabularies meet in one shell at M5 (see [../ARCHITECTURE.md](../ARCHITECTURE.md)). Gating only hides a surface; the server still authorizes behind it.
  - A context populated once, not a TanStack Query: it describes the server that served this page, so it cannot change without a reload, and signing out calls `queryClient.clear()`, which would drop it.
- Navigation is data, not markup: `src/app/nav/registry.ts` is the only place a destination is declared, and `AppShell` renders whatever it holds. An entry may declare three independent gates, which `src/app/nav/useNavVisibility.ts` composes as AND: `surface` (deployment), `capability` (entitlement), and `flag` (operational, only valid alongside a capability, which the type enforces). Any one hides the link, a section drops its heading with its last visible item, and the shell answers the route behind a hidden link with a "not available here" panel rather than a page the server would refuse every request of. Field names, composition, and mostly the wording match `otari-ai/frontend/src/app/nav` so the two registries compose at M5 rather than being reconciled; `icon` is the one deliberate difference, an inline element from `nav/icons.tsx` here and a `react-icons` `IconType` there.
  - `src/app/nav/overlaySections.ts` is the seam and is meant to stay empty here. An overlay owns its pages in its own tree and replaces this module at build time; `composeNavSections` appends whatever it exports after the base sections, so an overlay adds navigation without editing a base source file.
  - The entitlement and flag axes resolve through `src/shared/hooks/useEntitlements.tsx`, and **the base build answers both from a constant**: `BASE_CAPABILITIES` is what this build grants, flags are empty, `isLoading` is always false, and no provider is wired up (an overlay wires one). Both are **empty today and no base entry is tagged**, so the axes are mechanism without a base user yet. The hooks return `{ entitled, isLoading }` rather than bare booleans to match otari.ai, where both are TanStack queries, so the resolver can go async without touching a call site. Add a name to `BASE_CAPABILITIES` in the same commit as the entry that gates on it; `registry.test.ts` fails on the half of that pair a commit forgets.
  - `src/shared/components/EntitlementGate.tsx` is the component form of the same two gates, for wrapping a page or a block. The sidebar deliberately does not use it: a section heading has to disappear with its last visible item, which needs a predicate rather than a wrapper.
- Layout, and it is deliberately `otari-ai/frontend/src`'s layout, because the control-plane UI there moves into this repo at M5 and the smaller tree is the one that should move: `src/features/<domain>/` owns a domain end to end (its page, the components only it renders, its pure derivations, and their tests); `src/shared/` holds what no domain owns (`components/` primitives, `helpers/` pure functions, `api/` transport and TanStack Query hooks, `hooks/` the cross-cutting React state a feature may read); `src/app/` is the composition root and the shell chrome (`App`, `provider`, `router`, `AppShell`, `HybridLanding`, `ConnectionStatus`, `UpdatePrompt`, and `nav/`, the sidebar registry and its overlay seam); `src/routes/` maps URLs to feature pages; `src/tests/` holds the test harnesses; `src/client/` is the generated API client, `src/main.tsx` the entry, and `src/styles/globals.css` the one stylesheet.
  - `src/shared/api/` is the one directory with no counterpart over there, and deliberately so: the platform generates its transport with hey-api, while `api/client.ts` here is hand-written for the session exchange and the 401 bounce. Their `shared/` also has `constants/`, which ours will grow when there is something to put in it rather than as empty ceremony.
  - Three import rules hold it together, and Biome enforces them on every PR (`web/biome.jsonc`, `npm run lint`, a step in `otari-dashboard.yml`): **a feature may not import `src/app`**, **`src/shared` may not import `src/features` or `src/app`**, and **nothing may import an overlay's tree**. The rules, their spelling, and most of their wording are `otari-ai/frontend/biome.json`'s; keep them recognizably the same. Feature-to-feature is deliberately allowed: keys pick models, budgets pick users. `src/architecture.test.ts` plants a violation of each rule and proves Biome rejects it, so the rules cannot quietly stop being rules.
  - There is no overlay tree here and there is not meant to be one. An overlay owns its routes in `otari-ai` and is composed onto this base at build time as a sibling of `src/` (see [../ARCHITECTURE.md](../ARCHITECTURE.md)); the rule exists so the import that would only resolve in that superset build cannot be written here.
  - Biome also formats and runs the recommended rule set, both taken from `otari-ai/frontend`: two-space, double quotes, semicolons as needed, organized imports. `npm run lint` is `biome check`, which reports; `npm run lint:fix` is the one that writes. Do not reformat by hand or with another tool.
  - Where a recommended rule is suppressed, the suppression says why, at the site. Most of them exist because the rule cannot see through a custom component or a conditional role rather than because the code is wrong. Before adding another, check the rule is actually wrong: several of the findings this rule set first reported were real, including one introduced while writing these suppressions.
  - `src/tests/` sits outside the boundary on purpose, as it does over there: a harness exists to mount what the app mounts, so it is the one place that may import `src/app`. That is how a feature's test reaches the real providers (`src/tests/providers.tsx`) without importing the composition root itself.
- Design foundation, rehomed from `otari-ai/frontend/src/index.css`, which the architecture charter settles as canonical for the converged dashboard (mozilla-ai/otari#585, otari-ai#1591). `src/styles/globals.css` is the whole of it: self-hosted brand faces, the semantic `--color-*` / `--shadow-*` / `--field-*` tokens in a light block and a dark one, the `@theme` registrations, the seven-role type scale, the token-consuming base reset, and a few HeroUI v3 patches. The token families, the HeroUI variable mapping that makes a bare `<Card>` wear the palette with no `className`, the type scale, and what deliberately stayed behind in otari-ai are all in [design-tokens.md](../.github/skills/frontend-standards/design-tokens.md); read it before touching the stylesheet. Three things to know from here:
  - Keep it recognizably the same file as otari-ai's. The control-plane pages arrive at M5 and have to land on this palette without a reconciliation pass, so a divergence in a token's name, value, or reasoning comment costs more than it looks like it does.
  - **Everything below the `MIGRATION BRIDGE` marker is on its way out**, as is every `src/shared/components/` file carrying the matching header comment. Those are the pre-rehome `--otari-*` palette and the primitives built on it, kept at their original values only so existing pages keep rendering. Nothing new may consume one; converting a page is what retires its tokens. New primitives go in `src/shared/components/ui/`, the one tree where "semantic tokens only" is enforced rather than asked for.
  - `src/styles/foundation.test.ts` and `fonts.test.ts` are what hold both halves: a missing or literal-valued HeroUI mapping, theme blocks that stop declaring the same token set, an `--otari-*` declared above the marker, a raw hex under `components/ui/`, or a font face shipped without its license all fail there.
- Runtime search tools: the Tools & Guardrails page (`web/src/features/tools/ToolsGuardrailsPage.tsx`) renders `web/src/features/tools/SearchToolsCard.tsx`, which manages the `search_tool_credentials` table via `/v1/search-tools` (CRUD + `GET /providers` for the picker). Backend: `services/search_tool_store_service.py` overlays stored tools onto `config.search_tools` exactly as the provider store overlays `config.providers` (per-config baseline on `config._search_tool_baseline`, TTL refresher wired in the lifespan, standalone-only), so `POST /v1/search` no longer needs a config file. Config-file tools are listed read-only.
- Runtime provider management: the Providers page (`web/src/features/providers/ProvidersPage.tsx`) manages the `provider_credentials` table via `/v1/provider-credentials` (CRUD + `POST /{instance}/test`). Backend: `services/provider_store_service.py` overlays stored providers onto `config.providers` (per-config baseline on `config._provider_baseline`, refreshed by a TTL refresher wired in the lifespan like the alias refresher, standalone-only); `services/secret_box.py` encrypts keys with `OTARI_SECRET_KEY` (Fernet); `services/master_key_service.py` generates + prints a master key on first run when none is set (hash in `runtime_settings`). Keys are write-only over the API (responses expose only `last4`).
- Build: `make dashboard` from the repo root (`npm --prefix web ci && npm --prefix web run build`). Output goes to `src/gateway/static/dashboard/` (set in `web/vite.config.ts`), which is gitignored, not committed: Vite content-hashes every asset filename, so a committed bundle turned any two branches touching `web/src` into a merge conflict. Consequences: the Docker image builds the bundle in a `node:22-slim` stage (`Dockerfile`), a source checkout without a build degrades to the tutorial page (`gateway/dashboard.py` returns `None`), and a wheel ships the dashboard only if `make dashboard` ran first. There is nothing to commit after a `web/src` change.
- Bundled user guide: the dashboard renders `docs/dashboard.md` at `/#/docs` (linked from the sidebar footer) by importing it with Vite's `?raw` (`web/src/features/docs/DocsPage.tsx`), so the running dashboard ships the guide it matches. The guide lives outside `web/`, so `web/vite.config.ts` grants `server.fs` access to it. Because it is a build input from outside `web/`, it is also a Docker image input: `.dockerignore` excludes `docs/` but re-includes this one file, and `otari-docker.yml` triggers on it.
- Home-screen install (PWA): `web/public/pwa/` holds the web app manifest and the PNG app icons (`icon-192`, `icon-512`, a `maskable` 512, and an `apple-touch-icon` for iOS), all generated from the Otari mark in `web/public/favicon.svg` (white mark on `--otari-brand`). Vite copies the directory into the bundle and `src/gateway/main.py` mounts it at `/pwa` alongside the dashboard, so it is standalone-only; `web/index.html` links the manifest plus the `apple-*`/`theme-color` meta tags. There is deliberately no service worker: Chrome dropped the fetch-handler requirement for menu installs, and the dashboard is live API data with nothing worth caching offline.
- API client: every request and response shape comes from `web/src/client/schema.ts`, generated from `docs/public/openapi.json` by `npm run client:generate` (also run by `pretest`, so `npm test` keeps it current) and committed with a CI drift check, for the same reason as the route tree. `web/src/client/index.ts` is the only hand-written part and declares no structure: it aliases the generated schemas to the names the dashboard uses (`User` for `UserResponse`, `ApiKey` for `KeyInfo`), derives the query-parameter enums from their operations, and holds the few runtime guards that narrow a generated union (`isUnitChargeLine`, `isPricingTier`). Import types from `@/client`, never from `./schema` directly.
  - `web/src/client/local.ts` is the exception list, and it is meant to stay short: routing-policy bodies (the wire contract declares `spec` a free-form object), `/dashboard-build.json` (a static file, not an API route), and `UsageFilters` (query parameters the hooks assemble, never a body). Each says why. Anything else hand-written here will drift from the API silently.
  - `web/src/shared/api/client.ts` stays hand-written on purpose: the session exchange, the 401 bounce, and the two-tier request timeouts are transport policy no generator emits.
  - Two traps the generator sets. A schema field with a **default** is emitted as required, which is right for a response and wrong for a request body the client may omit; `Defaulted<T, K>` in `index.ts` corrects the few that bite. And a fixture that omits a field is not the same as one that sets it to zero: `billedTokenTotal` and the share-card caveats both branch on `undefined`, so `src/tests/fixtures.ts` builders fill a whole shape while `shareCardData.test.ts` deliberately keeps its own that does not.
- Routing: TanStack Router with file-based routes in `web/src/routes/`, one file per URL, assembled into `src/routeTree.gen.ts` by the Vite plugin (`@tanstack/router-plugin`) and wired up in `src/app/router.tsx`. The generated tree is committed, because `npm run typecheck` runs `tsc` alone and never invokes Vite; it is regenerated by any `npm test`/`npm run build`, so a stale one shows up as a dirty file. Three rules to keep:
  - **A route file exports `Route` and nothing else**, which is what lets `autoCodeSplitting` lift each page into its own chunk; `src/routes.test.ts` enforces it. Page components live in `src/features/<domain>/` and the route file only names one.
  - **Search params are flat strings, with a repeated key (`?model=a&model=b`) as that filter's value set.** The router is given the codec in `src/shared/helpers/search.ts` for this; TanStack's default would JSON-encode them and rewrite every shared link. `validateSearch` sits on the root route so any route may carry any of the filters the pages read. Read and write them through `useUrlState` (`src/shared/helpers/urlState.ts`), never by hand.
  - **A component test needs a real router**, since the pages keep filters and pagination in the URL: `withRouter` / `renderWithRouter` from `src/tests/router.tsx`. The router resolves its first location asynchronously, so a test that reads the DOM (or a hook result) synchronously has to `await renderWithRouter` or `flushRouter` first.
- Checks: `npm --prefix web run lint` (formatting, the recommended rules, and the layer boundaries; `lint:fix` writes), `npm --prefix web run typecheck`, `npm --prefix web test`. CI runs these plus a build, to prove the bundle the Docker image produces still compiles (`.github/workflows/otari-dashboard.yml`).
- End-to-end (`web/e2e`, `npm --prefix web run e2e`, also a CI job): Playwright against a real gateway serving the freshly built bundle (`e2e/serve.sh` wipes a SQLite DB and boots standalone). Three ordered projects share that one database; `playwright.config.ts` declares the order and why. Two rules the config cannot state: because these pages are gateway-wide, **a spec scopes itself to the rows it owns** rather than to a global count, and an open react-aria combobox popover `aria-hidden`s the rest of the page, so `dismissComboBox` (`e2e/helpers.ts`) has to run before asserting anything outside it.
- Serving: standalone mode serves `index.html` at `/`, hashed assets under `/assets`, and the two non-hashed directories the page names by absolute path, `/pwa` and `/fonts` (`src/gateway/main.py`, `src/gateway/dashboard.py`). The tutorial moved to `/welcome`, and hybrid mode keeps serving it at `/`, having no local management API. Routing is hash history (`/#/routing`, and `/#/aliases` redirects there), so there is deliberately **no catch-all** and the API/asset paths are never shadowed. The cost of that: a new non-hashed directory reaches a browser only with its own `app.mount` and a `static/dashboard/<dir>/*` glob in `pyproject.toml`'s package data, and those globs do not recurse, so missing either 404s silently. A `_SHORT_CACHE_PREFIXES` entry is separate and is about policy, not availability: without one the security middleware falls through to `private, no-store, no-cache`, and the whole directory is re-fetched on every page load. `otari-ai/frontend` needs none of it, serving its whole `dist/` from one nginx `location /`; the two trees agree on the URL and differ only in what answers it.
