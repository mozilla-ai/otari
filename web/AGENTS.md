# Web Dashboard (`web/`)

`web/CLAUDE.md` is a one-line `@AGENTS.md` import of this file. Always edit `AGENTS.md` directly; never modify `CLAUDE.md`, and do not delete it: Claude Code discovers `CLAUDE.md`, not `AGENTS.md`, so the import is what loads this file.

Loaded when working under `web/`. For house style (HeroUI v3, `--otari-*` design
tokens, TanStack Query, Vitest), read
[../.github/skills/frontend-standards/SKILL.md](../.github/skills/frontend-standards/SKILL.md).

- The standalone admin dashboard is a React + HeroUI v3 SPA in `web/` (Vite, Tailwind v4, TanStack Query). It browses the model catalog, sets model pricing, manages routing policies (which absorbed the old Aliases page), adds/edits provider API keys, and toggles runtime settings; it calls the management API (`/v1/models`, `/v1/pricing`, `/v1/routing/policies`, `/v1/aliases`, `/v1/provider-credentials`, `/v1/settings`) as the master key: entered once on a sign-in screen, the key is exchanged (`POST /v1/auth/session`) for an HttpOnly session cookie with a TTL (`dashboard_session_ttl_hours`, table `dashboard_sessions`), so the raw key is never persisted in the browser and a sign-in survives tab closes and restarts. The auth dependencies in `api/deps.py` accept the cookie only when a request carries no header credentials; master-key rotation revokes every session and re-mints the caller's.
- Layout, and it is deliberately `otari-ai/frontend/src`'s layout, because the control-plane UI there moves into this repo at M5 and the smaller tree is the one that should move: `src/features/<domain>/` owns a domain end to end (its page, the components only it renders, its pure derivations, and their tests); `src/shared/` holds what no domain owns (`components/` primitives, `helpers/` pure functions, `api/` transport and TanStack Query hooks); `src/app/` is the composition root and the shell chrome (`App`, `provider`, `router`, `AppShell`, `ConnectionStatus`, `UpdatePrompt`); `src/routes/` maps URLs to feature pages; `src/tests/` holds the test harnesses; `src/client/` is the generated API client, `src/main.tsx` the entry, and `src/styles/globals.css` the one stylesheet.
  - `src/shared/api/` is the one directory with no counterpart over there, and deliberately so: the platform generates its transport with hey-api, while `api/client.ts` here is hand-written for the session exchange and the 401 bounce. Their `shared/` also has `constants/` and `hooks/`; ours will grow them when there is something to put in them, rather than as empty ceremony.
  - Three import rules hold it together, and Biome enforces them on every PR (`web/biome.jsonc`, `npm run lint`, a step in `otari-dashboard.yml`): **a feature may not import `src/app`**, **`src/shared` may not import `src/features` or `src/app`**, and **nothing may import an overlay's tree**. The rules, their spelling, and most of their wording are `otari-ai/frontend/biome.json`'s; keep them recognizably the same. Feature-to-feature is deliberately allowed: keys pick models, budgets pick users. `src/architecture.test.ts` plants a violation of each rule and proves Biome rejects it, so the rules cannot quietly stop being rules.
  - There is no overlay tree here and there is not meant to be one. An overlay owns its routes in `otari-ai` and is composed onto this base at build time as a sibling of `src/` (see [../ARCHITECTURE.md](../ARCHITECTURE.md)); the rule exists so the import that would only resolve in that superset build cannot be written here.
  - Biome also formats and runs the recommended rule set, both taken from `otari-ai/frontend`: two-space, double quotes, semicolons as needed, organized imports. `npm run lint` is `biome check`, which reports; `npm run lint:fix` is the one that writes. Do not reformat by hand or with another tool.
  - Where a recommended rule is suppressed, the suppression says why, at the site. Most of them exist because the rule cannot see through a custom component or a conditional role rather than because the code is wrong. Before adding another, check the rule is actually wrong: several of the findings this rule set first reported were real, including one introduced while writing these suppressions.
  - `src/tests/` sits outside the boundary on purpose, as it does over there: a harness exists to mount what the app mounts, so it is the one place that may import `src/app`. That is how a feature's test reaches the real providers (`src/tests/providers.tsx`) without importing the composition root itself.
- Runtime search tools: the Tools & Guardrails page (`web/src/features/tools/ToolsGuardrailsPage.tsx`) renders `web/src/features/tools/SearchToolsCard.tsx`, which manages the `search_tool_credentials` table via `/v1/search-tools` (CRUD + `GET /providers` for the picker). Backend: `services/search_tool_store_service.py` overlays stored tools onto `config.search_tools` exactly as the provider store overlays `config.providers` (per-config baseline on `config._search_tool_baseline`, TTL refresher wired in the lifespan, standalone-only), so `POST /v1/search` no longer needs a config file. Config-file tools are listed read-only.
- Runtime provider management: the Providers page (`web/src/features/providers/ProvidersPage.tsx`) manages the `provider_credentials` table via `/v1/provider-credentials` (CRUD + `POST /{instance}/test`). Backend: `services/provider_store_service.py` overlays stored providers onto `config.providers` (per-config baseline on `config._provider_baseline`, refreshed by a TTL refresher wired in the lifespan like the alias refresher, standalone-only); `services/secret_box.py` encrypts keys with `OTARI_SECRET_KEY` (Fernet); `services/master_key_service.py` generates + prints a master key on first run when none is set (hash in `runtime_settings`). Keys are write-only over the API (responses expose only `last4`).
- Build: `make dashboard` from the repo root (`npm --prefix web ci && npm --prefix web run build`). Output goes to `src/gateway/static/dashboard/` (set in `web/vite.config.ts`), which is gitignored, not committed: Vite content-hashes every asset filename, so a committed bundle turned any two branches touching `web/src` into a merge conflict. Consequences: the Docker image builds the bundle in a `node:22-slim` stage (`Dockerfile`), a source checkout without a build degrades to the tutorial page (`gateway/dashboard.py` returns `None`), and a wheel ships the dashboard only if `make dashboard` ran first. There is nothing to commit after a `web/src` change.
- Bundled user guide: the dashboard renders `docs/dashboard.md` at `/#/docs` (linked from the sidebar footer) by importing it with Vite's `?raw` (`web/src/features/docs/DocsPage.tsx`), so the running dashboard ships the guide it matches. The guide lives outside `web/`, so `web/vite.config.ts` grants `server.fs` access to it. Because it is a build input from outside `web/`, it is also a Docker image input: `.dockerignore` excludes `docs/` but re-includes this one file, and `otari-docker.yml` triggers on it.
- Home-screen install (PWA): `web/public/pwa/` holds the web app manifest and the PNG app icons (`icon-192`, `icon-512`, a `maskable` 512, and an `apple-touch-icon` for iOS), all generated from the Otari mark in `web/public/favicon.svg` (white mark on `--otari-brand`). Vite copies the directory into the bundle and `src/gateway/main.py` mounts it at `/pwa` alongside the dashboard, so it is standalone-only; `web/index.html` links the manifest plus the `apple-*`/`theme-color` meta tags. There is deliberately no service worker: Chrome dropped the fetch-handler requirement for menu installs, and the dashboard is live API data with nothing worth caching offline.
- API client: every request and response shape comes from `web/src/client/schema.ts`, generated from `docs/public/openapi.json` by `npm run client:generate` (also run by `pretest`, so `npm test` keeps it current) and committed with a CI drift check, for the same reason as the route tree. `web/src/client/index.ts` is the only hand-written part and declares no structure: it aliases the generated schemas to the names the dashboard uses (`User` for `UserResponse`, `ApiKey` for `KeyInfo`), derives the query-parameter enums from their operations, and holds the few runtime guards that narrow a generated union (`isUnitChargeLine`, `isPricingTier`). Import types from `@/client`, never from `./schema` directly.
  - `web/src/client/local.ts` is the exception list, and it is meant to stay short: routing-policy bodies (the wire contract declares `spec` a free-form object), `/dashboard-build.json` (a static file, not an API route), and `UsageFilters` (query parameters the hooks assemble, never a body). Each says why. Anything else hand-written here will drift from the API silently.
  - `web/src/shared/api/client.ts` stays hand-written on purpose: the session exchange, the 401 bounce, and the two-tier request timeouts are transport policy no generator emits.
  - Two traps the generator sets. A schema field with a **default** is emitted as required, which is right for a response and wrong for a request body the client may omit; `Defaulted<T, K>` in `index.ts` corrects the few that bite. And a fixture that omits a field is not the same as one that sets it to zero: `billedTokenTotal` and the share-card caveats both branch on `undefined`, so `src/tests/fixtures.ts` builders fill a whole shape while `shareCardData.test.ts` deliberately keeps its own that does not.
- Routing: TanStack Router with file-based routes in `web/src/routes/`, one file per URL, assembled into `src/routeTree.gen.ts` by the Vite plugin (`@tanstack/router-plugin`) and wired up in `src/app/router.tsx`. The generated tree is committed, because `npm run typecheck` runs `tsc` alone and never invokes Vite; it is regenerated by any `npm test`/`npm run build`, so a stale one shows up as a dirty file. Three rules to keep:
  - **A route file exports `Route` and nothing else**, which is what lets `autoCodeSplitting` lift each page into its own chunk; `src/routes.test.ts` enforces it. Page components live in `src/features/<domain>/` and the route file only names one.
  - **Search params are flat strings, with a repeated key (`?model=a&model=b`) as that filter's value set.** The router is given the codec in `src/shared/helpers/search.ts` for this; TanStack's default would JSON-encode them and rewrite every shared link. `validateSearch` sits on the root route so any route may carry any of the filters the pages read. Read and write them through `useUrlState` (`src/shared/helpers/urlState.ts`), never by hand.
  - **A component test needs a real router**, since the pages keep filters and pagination in the URL: `withRouter` / `renderWithRouter` from `src/tests/router.tsx`. The router resolves its first location asynchronously, so a test that reads the DOM (or a hook result) synchronously has to `await renderWithRouter` or `flushRouter` first.
- Checks: `npm --prefix web run lint` (formatting, the recommended rules, and the layer boundaries; `lint:fix` writes), `npm --prefix web run typecheck`, `npm --prefix web test`. CI runs these plus a build, to prove the bundle the Docker image produces still compiles (`.github/workflows/otari-dashboard.yml`).
- End-to-end (`web/e2e`, `npm --prefix web run e2e`, also a CI job): Playwright against a real gateway serving the freshly built bundle (`e2e/serve.sh` wipes a SQLite DB and boots standalone; `e2e/otari.yml` fixes the master key). Three ordered projects share that one database, so the order is declared in `playwright.config.ts` rather than left to filename sort: `onboarding` (`dashboard.spec.ts`) needs the empty DB and asserts the first-run screens; `seed` (`parity.setup.ts`) imports the usage fixture in `e2e/parity-data.ts` through `POST /v1/usage/external-events`, which writes real priced usage rows with no upstream to reach; `parity` (everything else) then asserts Overview, Activity, Usage and the management pages behave. These pages are gateway-wide, so each spec scopes itself to what it owns rather than to a global count: Activity filters on the fixture's `source`, Usage names its models, sessions and users, the management specs create and remove their own objects, and Overview asserts a floor because its tiles cannot be filtered at all. Shared locators live in `e2e/helpers.ts`; note that an open react-aria combobox popover `aria-hidden`s the rest of the page, so `dismissComboBox` has to run before asserting anything outside it.
- Serving: standalone mode serves `index.html` at `/` and hashed assets under `/assets` (`src/gateway/main.py`, `src/gateway/dashboard.py`); the get-started tutorial moved to `/welcome`. Hybrid mode has no local management API, so `/` keeps serving the tutorial. Client-side routing is TanStack Router on hash history (routes live under `/#/providers`, `/#/models`, `/#/routing`, `/#/settings`; `/#/aliases` redirects to `/#/routing`, which absorbed it), so hash routes need no server catch-all and the API/asset paths are never shadowed.
