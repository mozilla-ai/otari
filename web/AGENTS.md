# Web Dashboard (`web/`)

`web/CLAUDE.md` is a one-line `@AGENTS.md` import of this file. Always edit `AGENTS.md` directly; never modify `CLAUDE.md`, and do not delete it: Claude Code discovers `CLAUDE.md`, not `AGENTS.md`, so the import is what loads this file.

Loaded when working under `web/`. For house style (HeroUI v3, the semantic design
tokens, TanStack Query, responsiveness, layout stability, testing), read
[../.github/skills/frontend-standards/SKILL.md](../.github/skills/frontend-standards/SKILL.md)
and the topic guide beside it that matches the change.

- The standalone admin dashboard is a React + HeroUI v3 SPA in `web/` (Vite, Tailwind v4, TanStack Query): model catalog, pricing, routing policies, provider keys, users, budgets, usage, runtime settings. It calls the management API on a session: a credential is entered once on a sign-in screen and exchanged (`POST /v1/auth/session`) for an HttpOnly session cookie with a TTL (`dashboard_session_ttl_hours`, table `dashboard_sessions`), so the *credential* is never persisted in the browser while the cookie is, which is what makes a sign-in survive tab closes and restarts without anything on the page being able to read it. Which credential that endpoint accepts depends on the deployment and is published in `GET /v1/bootstrap`'s `sign_in_methods`: the master key until an identity has a password, email and password from then on (otari#649). `Login.tsx` renders whichever of the two the bootstrap reports, so the master-key box is gone on a claimed deployment (otari-ai#1716's requirement, and #653's first row). The other nine auth routes #653 lists (signup, verification, reset, the OAuth callbacks, passkeys) are still to come, and this screen deliberately offers no link to them: nothing would answer one yet.
  - **Behind the session, `src/features/account/` owns the credential** (`/account`, `PUT /v1/auth/password`), which is the other half of the same endpoint pair and the destination the account menu names. One card and two forms, chosen from `sign_in_methods` the way the sign-in screen chooses: `master_key` means no identity holds a password, so the form claims the deployment (address plus password, no current one to prove); otherwise it changes a password and the server requires the current one, since this dashboard is always cookie-authenticated. Claiming would leave the bootstrap context stale, and it cannot be refetched, so the card reports the claim through `useRetireMasterKeySignIn` and the provider serves the corrected `sign_in_methods` from then on. That is the one field of the bootstrap this app may change, and it moves every consumer at once on purpose: the card switching forms, the account menu's session line, and the sign-in screen a later sign-out lands on are the same fact three times, and a tab where only the card had noticed would offer a credential the gateway had just stopped accepting. Deliberately not a row on the Settings page: everything there is a gateway-wide setting an operator changes on behalf of the process, and this is the credential identifying the person changing them. The one call it cannot make is the master-key recovery of a forgotten password, which needs a header rather than the session that reaching the page depends on. The auth dependencies in `api/deps.py` accept the cookie only when a request carries no header credentials; master-key rotation revokes every session and re-mints the caller's, and a password change revokes that identity's others.
- Deployment bootstrap: `src/main.tsx` fetches `GET /v1/bootstrap` (`src/gateway/api/routes/bootstrap.py`, mounted in both modes, unauthenticated) *before* it mounts React and hands the answer to `App`, which picks one of three roots from it: the hybrid landing page, the sign-in screen, or the router. A bootstrap that did not answer is an error state, never a guessed deployment. Below that, `src/shared/hooks/useDeployment.tsx` provides it, so a feature reads `useDeployment()` / `useSurfaces()` and no page component branches on the gateway's mode. The OSS half of the contract in mozilla-ai/otari-ai#1591, which is why the enum carries values (`hosted`, `hosted_user`) this gateway never produces.
  - A *surface* is the deployment axis: the management API groups a standalone gateway serves (`STANDALONE_SURFACES`), which is why a nav item gates on `usage` rather than "Activity", both being views over `/v1/usage`. A hybrid gateway hosts none. Deliberately **not** called capabilities, which otari.ai spends on the entitlement axis; the two vocabularies meet in one shell at M5 (see [../ARCHITECTURE.md](../ARCHITECTURE.md)). Gating only hides a surface; the server still authorizes behind it.
  - A context populated once, not a TanStack Query: it describes the server that served this page, so it cannot change without a reload, and signing out calls `queryClient.clear()`, which would drop it.
- Navigation is data, not markup: `src/app/nav/registry.ts` is the only place a *rail* destination is declared, and `AppShell` renders whatever it holds. The two exceptions are chrome, not navigation, and are listed in their own sub-bullet below. An entry may declare three independent gates, which `src/app/nav/useNavVisibility.ts` composes as AND: `surface` (deployment), `capability` (entitlement), and `flag` (operational, only valid alongside a capability, which the type enforces). Any one hides the link, a section drops its heading with its last visible item, and the shell answers the route behind a hidden link with a "not available here" panel rather than a page the server would refuse every request of. Field names, composition, and mostly the wording match `otari-ai/frontend/src/app/nav` so the two registries compose at M5 rather than being reconciled, `icon` included: it is a `react-icons` `IconType` in both, drawn from the same Feather set, so a destination that exists in both rails wears the same mark.
  - **Two rails, not one.** `NAV_SECTIONS` is the default (the workspace rail) and is scoped by the switcher above it; `ORG_NAV_SECTIONS` holds what belongs to the tenant, and `navContextForPath` decides which of the two a URL is under, so a route rather than a click owns the rail. Each rail composes its own overlay export (`OVERLAY_NAV_SECTIONS`, `OVERLAY_ORG_NAV_SECTIONS`). Two departures from otari-ai to know about before reconciling: **the org/workspace split is ours** (otari-ai keeps organization settings inside one tree), and **nesting is `children`/`NavChild` here** where otari-ai has `NavDisclosure`. A `NavChild` may carry its own `surface`, which is how Guardrails sits under Routing while being served by the `tools` surface. `navLabelForPath` and `NAV_CHILD_PARENTS` are what let the breadcrumbs name a nested destination without a second table to keep in step.
  - **A nav entry points at a page, never at a redirect.** The shell highlights on `currentPath === child.to`, so an entry whose target `beforeLoad`-redirects elsewhere can never be the active one and duplicates whatever it lands on. `/aliases` is the live example: it redirects onto `/routing`, so it is deliberately not in the registry.
  - **Two routes are reached from the chrome and are deliberately not in the registry**, which is a different exemption from `/aliases`: those are destinations the design draws outside the rails, not entries that could not work in them. `/docs` is in the top bar (`TopBarActions`) and in the account menu below `md`; `/account` is the account menu's own first row. Registering either would put it in the workspace rail *as well*, since the registry is what the rails render, and duplicate a row the design draws once. So a chrome destination is a hand-written `Link` on purpose, and the rule above is about the rails. Anything reached from the sidebar still belongs in the registry, gates included; if you are adding a rail item, that rule has no exception.
  - `src/app/nav/overlaySections.ts` is the seam and is meant to stay empty here. An overlay owns its pages in its own tree and replaces this module at build time; `composeNavSections` appends whatever it exports after the base sections, so an overlay adds navigation without editing a base source file.
  - `src/app/nav/overlayLabelOverrides.ts` is the second seam, empty here for the same reason, and covers the case appending a section cannot: renaming a label the base declares. `applyNavLabelOverrides` replaces a section's heading and the labels of the groups inside it, matched by `sectionId` and by the group's own path, and runs on both rails from the one list before `composeNavSections` appends anything. Same name, type (`NavLabelOverride`) and helper as `otari-ai/frontend/src/app/nav`, whose two field names differ where the shapes do (a heading is `label` here and `header` there; nesting is `children` here, so a rename names the path it targets).
  - The entitlement and flag axes resolve through `src/shared/hooks/useEntitlements.tsx`, and **the base build answers both from a constant**: `BASE_CAPABILITIES` is what this build grants, flags are empty, `isLoading` is always false, and no provider is wired up (an overlay wires one). Both are **empty today and no base entry is tagged**, so the axes are mechanism without a base user yet. The hooks return `{ entitled, isLoading }` rather than bare booleans to match otari.ai, where both are TanStack queries, so the resolver can go async without touching a call site. Add a name to `BASE_CAPABILITIES` in the same commit as the entry that gates on it; `registry.test.ts` fails on the half of that pair a commit forgets.
  - `src/shared/components/EntitlementGate.tsx` is the component form of the same two gates, for wrapping a page or a block. The sidebar deliberately does not use it: a section heading has to disappear with its last visible item, which needs a predicate rather than a wrapper.
- Layout, and it is deliberately `otari-ai/frontend/src`'s layout, because the control-plane UI there moves into this repo at M5 and the smaller tree is the one that should move: `src/features/<domain>/` owns a domain end to end (its page, the components only it renders, its pure derivations, and their tests); `src/shared/` holds what no domain owns (`components/` primitives, `helpers/` pure functions, `api/` transport and TanStack Query hooks, `hooks/` the cross-cutting React state a feature may read); `src/app/` is the composition root and the shell chrome (`App`, `provider`, `router`, `AppShell`, `HybridLanding`, `ConnectionStatus`, `UpdatePrompt`, and `nav/`, the sidebar registry and its overlay seam); `src/routes/` maps URLs to feature pages; `src/tests/` holds the test harnesses; `src/client/` is the generated API client, `src/main.tsx` the entry, and `src/styles/globals.css` the one stylesheet.
  - `src/shared/api/` is the one directory with no counterpart over there, and deliberately so: the platform generates its transport with hey-api, while `api/client.ts` here is hand-written for the session exchange and the 401 bounce. Their `shared/` also has `constants/`, which ours will grow when there is something to put in it rather than as empty ceremony.
  - Three import rules hold it together, and Biome enforces them on every PR (`web/biome.jsonc`, `pnpm run lint`, a step in `otari-dashboard.yml`): **a feature may not import `src/app`**, **`src/shared` may not import `src/features` or `src/app`**, and **nothing may import an overlay's tree**. The rules, their spelling, and most of their wording are `otari-ai/frontend/biome.json`'s; keep them recognizably the same. Feature-to-feature is deliberately allowed: keys pick models, budgets pick users. `src/architecture.test.ts` plants a violation of each rule and proves Biome rejects it, so the rules cannot quietly stop being rules.
  - There is no overlay tree here and there is not meant to be one. An overlay owns its routes in `otari-ai` and is composed onto this base at build time as a sibling of `src/` (see [../ARCHITECTURE.md](../ARCHITECTURE.md)); the rule exists so the import that would only resolve in that superset build cannot be written here.
  - Biome also formats and runs the recommended rule set, both taken from `otari-ai/frontend`: two-space, double quotes, semicolons as needed, organized imports. `pnpm run lint` is `biome check`, which reports; `pnpm run lint:fix` is the one that writes. Do not reformat by hand or with another tool.
  - Where a recommended rule is suppressed, the suppression says why, at the site. Most of them exist because the rule cannot see through a custom component or a conditional role rather than because the code is wrong. Before adding another, check the rule is actually wrong: several of the findings this rule set first reported were real, including one introduced while writing these suppressions.
  - `src/tests/` sits outside the boundary on purpose, as it does over there: a harness exists to mount what the app mounts, so it is the one place that may import `src/app`. That is how a feature's test reaches the real providers (`src/tests/providers.tsx`) without importing the composition root itself.
- Design foundation, rehomed from `otari-ai/frontend/src/index.css`, which the architecture charter settles as canonical for the converged dashboard (mozilla-ai/otari#585, otari-ai#1591). `src/styles/globals.css` is the whole of it: self-hosted brand faces, the semantic `--color-*` / `--shadow-*` / `--field-*` tokens in a light block and a dark one, the `@theme` registrations, the seven-role type scale, the token-consuming base reset, and a few HeroUI v3 patches. The token families, the HeroUI variable mapping that makes a bare `<Card>` wear the palette with no `className`, the type scale, and what deliberately stayed behind in otari-ai are all in [design-tokens.md](../.github/skills/frontend-standards/design-tokens.md); read it before touching the stylesheet. Three things to know from here:
  - Keep it recognizably the same file as otari-ai's. The control-plane pages arrive at M5 and have to land on this palette without a reconciliation pass, so a divergence in a token's name, value, or reasoning comment costs more than it looks like it does.
  - **"Semantic tokens only" is the whole tree's rule, not a directory's.** The pre-rehome `--otari-*` palette and the `MIGRATION BRIDGE` marker that fenced it are gone (mozilla-ai/otari#586), so nothing is exempt any more and `foundation.test.ts` enforces it over all of `src`. The `otari-` prefix that survives on a few **class** names (`.otari-table`, `.otari-markdown`) is the app's namespace for a hook that reaches into a HeroUI component's DOM, not a leftover variable; the namespace being sanctioned does not make the approach recommended, and the frontend-standards skill puts a rule like that last, after a variable, a shared utility, and the component's own props. Chart fills are the one family with no otari-ai counterpart (`--color-chart-cat-*`, `--color-chart-ramp-*`), validated per theme with the data-viz palette checker rather than picked by eye.
  - `src/styles/foundation.test.ts` and `fonts.test.ts` are what hold it together: a missing or literal-valued HeroUI mapping, theme blocks that stop declaring the same token set, an `--otari-*` variable declared again, a raw hex or numbered palette class anywhere under `src` (the one documented exception is `features/usage/ShareCard.tsx`, whose SVG is rasterized through an `<img>` where a custom property does not resolve), or a font face shipped without its license all fail there.
- Runtime search tools: the Tools & Guardrails page (`src/features/tools/ToolsGuardrailsPage.tsx`) renders `SearchToolsCard.tsx`, which manages the `search_tool_credentials` table via `/v1/search-tools` (CRUD + `GET /providers` for the picker). Config-file tools are listed read-only. The store that backs it is in [../src/gateway/AGENTS.md](../src/gateway/AGENTS.md).
- Runtime provider management: the Providers page (`src/features/providers/ProvidersPage.tsx`) manages the `provider_credentials` table via `/v1/provider-credentials` (CRUD + `POST /{instance}/test`). Keys are write-only over the API, so a response exposes only `last4` and the page can never render one back. The store, the encryption, and the first-run master key are in [../src/gateway/AGENTS.md](../src/gateway/AGENTS.md).
- Tenancy: `src/features/organization/` (General, Members, and the rate-overrides card on Model pricing) and `src/features/workspaces/` are the rehomed control-plane pages, gated on the `organizations` and `workspaces` surfaces and reading `/v1/organizations/me*` and `/v1/workspaces*`. They keep the platform's response shapes, which is the point: these are the pages `otari-ai/frontend` brings across at M5, so a renamed field would be reconciled twice. Six things follow from the OSS line and are worth knowing before editing them:
  - **One identity that can sign in.** Only an identity holding a password can, and only the bootstrap operator can be given one (`PUT /v1/auth/password` always acts on the caller's own identity), so a member added by address still holds a role and workspace access without being able to reach the gateway as themselves. That is what the Members page's copy says; it changes when signup and password reset land (otari#650), not before.
  - **`features/organization/roles.ts` is the client half of the server's rules**, not a second authority. It mirrors the fixed roles and the two refusals in `_validate_membership_update` (only an owner outranks an owner; the last active owner cannot be demoted or suspended) so a control that would be refused is disabled with a reason instead of erroring on click. `features/workspaces/` imports it, which is the feature-to-feature the boundary rules allow.
  - **One organization, and the page says so.** A self-hosted gateway is one tenant with several people in it, so the gateway mounts no create, switch, or delete endpoint and General offers no control for one. Adding those back is additive and belongs behind the entitlement gate an overlay contributes ([ARCHITECTURE.md](../ARCHITECTURE.md)), not in the base page.
  - **Rate overrides are a section of Model pricing, not a page of their own.** `features/organization/RateOverridesCard.tsx` renders inside `features/pricing/ModelPricingPage.tsx`, reading `/v1/organizations/me/pricing`. That page owns the deployment catalog; this is the organization's own rates *above* it, and a request resolves the override first and the catalog row second (`services/pricing_service.py`). Kept as two cards on one page rather than two destinations, because an operator asking "what does this model cost us" is asking one question, while merging the two tables into a single list would hide which of the two a bill came from. Periods are half-open, so two may meet at an instant without overlapping, and overlapping periods for one model are refused with a 409; `features/organization/pricingOverride.ts` is the client half of that rule, disabling a doomed save, and the server's refusal is still the authority.
  - **Invitations are ported** (otari#641): `POST /me/member-invitations` lands a membership `invited` and emails an accept link if mail is configured (see [../src/gateway/AGENTS.md](../src/gateway/AGENTS.md)). Mail is optional, so the form reads `mail_ready` off the bootstrap and says which of the two outcomes to expect *before* the invite, and the result shows the accept link whenever it was not emailed; a mail-dependent surface with no such fallback gates on the same flag and is absent instead (otari#648). `src/features/invitations/AcceptInvitationPage.tsx` is the public page the link lands on, gated on nothing (the token is the whole credential) rather than on a surface. It is deliberately not one of `src/routes/`'s files, since every route there sits behind the session gate `App.tsx`'s `DeploymentRoot` puts in front of the router, and the recipient of an invitation holds neither a session nor the master key; `DeploymentRoot` renders it directly, keyed on the hash, ahead of that gate.
  - **Not ported, each waiting on its own backend slice**: email-domain auto-join, teams, and the organization dashboard aggregates. Nothing here should grow a placeholder for them. Distinct from the four rows the organization rail *declares and gates off* (Billing, Gateways, the organization's own provider credentials, and the guardrail ceiling): those are navigation the design draws, gated on a `surface` `STANDALONE_SURFACES` does not report so the link is absent here and present on a deployment that serves them. See `nav/registry.ts` for why the gate is on that axis and not the capability one.
- Toolchain: **pnpm**, pinned by `packageManager` in `web/package.json`, which is where CI (`pnpm/action-setup`), the Docker web stage (corepack) and `make dashboard` all read the version from. Two consequences of pnpm's isolated `node_modules` that npm's hoisting used to hide. A dependency the app shares with HeroUI has to resolve to **one** copy or the two get separate module instances and the context between them breaks: `react-aria-components` is pinned exactly to HeroUI's version for that reason, and a `^` there is a bug, not a convenience. And a dependency's install script does not run unless it is approved in `pnpm-workspace.yaml` (`allowBuilds`), which is what links esbuild's binary; without the entry every install fails the pre-run check rather than the build failing later. pnpm also does not run npm-style `pre`/`post` scripts, so anything that used one is chained explicitly in `package.json`. One version range is deliberately not the newest available: `@types/node` tracks the Node major that *builds* this bundle, which is 22 (the Docker web stage's `node:22-slim` and `node-version: 22` in the dashboard workflows). Raising it to the newest line would typecheck calls to APIs those runtimes do not have, so it moves when they do. And `typescript` stays on the 5 line: TypeScript 7 is the native compiler, whose package exports only `version` where the old JS API used to be, and `openapi-typescript` builds `src/client/schema.ts` through that API (`ts.factory`), so it exits before writing a file. Moving to 7 means finding a generator that does not need the API, not bumping the pin.
- React Compiler: `babel-plugin-react-compiler` runs as its own Babel pass in `web/vite.config.ts` (`@rolldown/plugin-babel`, configured by the `reactCompilerPreset` helper `@vitejs/plugin-react` exports), which is where that plugin's version 6 left it after dropping the `babel` option it used to host. Deliberately not `react({ compiler: true })`, whose oxc-transform-react is a different implementation of the same compiler and still experimental. The same pass `otari-ai/frontend` runs. Components and derived values are memoized at build time, so hand-written `useMemo`/`useCallback`/`React.memo` needs a reason; effects and their dependency arrays are unaffected. It bails out silently on a component that breaks the rules of hooks, which is the one way to lose the optimization without noticing.
- Build: `make dashboard` from the repo root (installs from the lockfile when it is stale, then `pnpm --dir web run build`). Output goes to `src/gateway/static/dashboard/` (set in `web/vite.config.ts`), which is gitignored, not committed: Vite content-hashes every asset filename, so a committed bundle turned any two branches touching `web/src` into a merge conflict. Consequences: the Docker image builds the bundle in a `node:22-slim` stage (`Dockerfile`), a source checkout without a build degrades to the tutorial page (`gateway/dashboard.py` returns `None`), and a wheel ships the dashboard only if `make dashboard` ran first. There is no *bundle* to commit after a `web/src` change, which is not the same as nothing: the route tree and the API client below are committed, and a change that adds a route or moves the spec leaves one of them to commit.
- Bundled user guide: the dashboard renders `docs/dashboard.md` at `/#/docs` (reached from **Documentation** in the top bar, `src/app/nav/TopBarActions.tsx`; that cluster is `hidden md:flex`, so the account menu carries the same row under `md:hidden`, which is what keeps the guide reachable on a phone, where the menu renders inside the drawer) by importing it with Vite's `?raw` (`web/src/features/docs/DocsPage.tsx`), so the running dashboard ships the guide it matches. The guide lives outside `web/`, so `web/vite.config.ts` grants `server.fs` access to it. Because it is a build input from outside `web/`, it is also a Docker image input: `.dockerignore` excludes `docs/` but re-includes this one file, and `otari-docker.yml` triggers on it.
- Home-screen install (PWA): `web/public/pwa/` holds the web app manifest and the PNG app icons (`icon-192`, `icon-512`, a `maskable` 512, and an `apple-touch-icon` for iOS), all generated from the Otari mark in `web/public/favicon.svg` (white mark on the brand teal). Vite copies the directory into the bundle and `src/gateway/main.py` mounts it at `/pwa`, standalone-only even though the bundle around it is now served in both modes: a hybrid gateway's root is a status page for a control plane that lives elsewhere, and an installed icon named "Otari Dashboard" would promise management it does not have. `web/index.html` links the manifest plus the `apple-*`/`theme-color` meta tags either way, so in hybrid that link 404s, which is what stops a browser offering the install. There is deliberately no service worker: Chrome dropped the fetch-handler requirement for menu installs, and the dashboard is live API data with nothing worth caching offline.
- API client: every request and response shape comes from `web/src/client/schema.ts`, generated from `docs/public/openapi.json` by `pnpm run client:generate` (chained into `pnpm test`, so the suite keeps it current; pnpm does not run npm-style `pre` scripts, which is why the chain is explicit in `package.json`) and committed with a CI drift check, for the same reason as the route tree. `web/src/client/index.ts` is the only hand-written part and declares no structure: it aliases the generated schemas to the names the dashboard uses (`User` for `UserResponse`, `ApiKey` for `KeyInfo`), derives the query-parameter enums from their operations, and holds the few runtime guards that narrow a generated union (`isUnitChargeLine`, `isPricingTier`). Import types from `@/client`, never from `./schema` directly.
  - `web/src/client/local.ts` is the exception list, and it is meant to stay short: routing-policy bodies (the wire contract declares `spec` a free-form object), `/dashboard-build.json` (a static file, not an API route), and `UsageFilters` (query parameters the hooks assemble, never a body). Each says why. Anything else hand-written here will drift from the API silently.
  - `web/src/shared/api/client.ts` stays hand-written on purpose: the session exchange, the 401 bounce, and the two-tier request timeouts are transport policy no generator emits.
  - Two traps the generator sets. A schema field with a **default** is emitted as required, which is right for a response and wrong for a request body the client may omit; `Defaulted<T, K>` in `index.ts` corrects the few that bite. And a fixture that omits a field is not the same as one that sets it to zero: `billedTokenTotal` and the share-card caveats both branch on `undefined`, so `src/tests/fixtures.ts` builders fill a whole shape while `shareCardData.test.ts` deliberately keeps its own that does not.
- Routing: TanStack Router with file-based routes in `web/src/routes/`, one file per URL, assembled into `src/routeTree.gen.ts` by the Vite plugin (`@tanstack/router-plugin`) and wired up in `src/app/router.tsx`. The generated tree is committed, because `pnpm run typecheck` runs `tsc` alone and never invokes Vite; it is regenerated by any `pnpm test`/`pnpm run build`, so a stale one shows up as a dirty file. Three rules to keep:
  - **A route file exports `Route` and nothing else**, which is what lets `autoCodeSplitting` lift each page into its own chunk; `src/routes.test.ts` enforces it. Page components live in `src/features/<domain>/` and the route file only names one.
  - **Search params are flat strings, with a repeated key (`?model=a&model=b`) as that filter's value set.** The router is given the codec in `src/shared/helpers/search.ts` for this; TanStack's default would JSON-encode them and rewrite every shared link. `validateSearch` sits on the root route so any route may carry any of the filters the pages read. Read and write them through `useUrlState` (`src/shared/helpers/urlState.ts`), never by hand.
  - **A component test needs a real router**, since the pages keep filters and pagination in the URL: `withRouter` / `renderWithRouter` from `src/tests/router.tsx`. The router resolves its first location asynchronously, so a test that reads the DOM (or a hook result) synchronously has to `await renderWithRouter` or `flushRouter` first.
- Checks: `pnpm --dir web run lint` (formatting, the recommended rules, and the layer boundaries; `lint:fix` writes), `pnpm --dir web run typecheck`, `pnpm --dir web test`. CI runs these plus a build, to prove the bundle the Docker image produces still compiles (`.github/workflows/otari-dashboard.yml`).
- End-to-end (`web/e2e`, `pnpm --dir web run e2e`, also a CI job): Playwright against a real gateway serving the freshly built bundle (`e2e/serve.sh` wipes a SQLite DB and boots standalone). Three ordered projects share that one database; `playwright.config.ts` declares the order and why. Two rules the config cannot state: because these pages are gateway-wide, **a spec scopes itself to the rows it owns** rather than to a global count, and an open react-aria combobox popover `aria-hidden`s the rest of the page, so `dismissComboBox` (`e2e/helpers.ts`) has to run before asserting anything outside it.
- Screenshots (`web/e2e/screenshots`, `pnpm --dir web run e2e:screenshots`): the same Playwright harness, run as six projects, three viewports (1920, 1280, 390) times both themes. **The settings are `otari-ai/frontend`'s, ported rather than reinvented**, and worth keeping recognizably the same: real phone emulation for the mobile projects, a frozen clock, CSS animations and the scrollbar frozen out of the capture, SVG timelines paused, pinned locale and timezone, and two comparison budgets so a tall full-page capture cannot earn an allowance big enough to hide a changed paragraph. `.github/skills/frontend-standards/testing.md` explains each. The theme is seeded into localStorage before the first navigation so `index.html`'s pre-paint script applies it on frame one; recharts and relative timestamps are masked because neither is reproducible against a live gateway. The suite hangs off the `seed` project, not `parity`: the parity flows clean up after themselves, so depending on them only lets one flaky behavioral test take all 108 captures with it. **Not a PR gate, and no baselines are committed**: the CI job is `workflow_dispatch`-only and `e2e/screenshots/*-snapshots/` is gitignored, because pages still move as the migration onto the rehomed foundation lands. Dispatching the job captures the matrix on Linux and attaches it as an artifact, which a local macOS run cannot produce (its font rendering differs). Adding a page still means adding a line to whichever registry it belongs in, `authenticated.spec.ts` behind a session or `public.spec.ts` in front of one; that line is what covers it on a phone and in the dark once this becomes a gate, which is `pull_request` back in the job's condition, the `.gitignore` entry gone, and the captured set committed.
- Serving: the gateway serves `index.html` at `/`, hashed assets under `/assets`, and the two non-hashed directories the page names by absolute path, `/pwa` (standalone only, see above) and `/fonts` (`src/gateway/main.py`, `src/gateway/dashboard.py`). **Both modes serve the same bundle**, because which surfaces exist is the browser's question to ask once of `/v1/bootstrap`, not something this process answers by withholding files: hybrid boots the same page into `HybridLanding`. The tutorial moved to `/welcome` and is what `/` degrades to when no bundle was built, in either mode. Routing is hash history (`/#/routing`, and `/#/aliases` redirects there), so there is deliberately **no catch-all** and the API/asset paths are never shadowed. The cost of that: a new non-hashed directory reaches a browser only with its own `app.mount` and a `static/dashboard/<dir>/*` glob in `pyproject.toml`'s package data, and those globs do not recurse, so missing either 404s silently. A `_SHORT_CACHE_PREFIXES` entry is separate and is about policy, not availability: without one the security middleware falls through to `private, no-store, no-cache`, and the whole directory is re-fetched on every page load. `otari-ai/frontend` needs none of it, serving its whole `dist/` from one nginx `location /`; the two trees agree on the URL and differ only in what answers it.
